Roadmap

What's actually built, not what's promised.

Forge is built by one teacher, in a live classroom, subject by subject. Rather than a quarterly plan we can't guarantee, here's what's actually running, what's being finished, and what's genuinely next — grouped by how real it is, not by when we hope to ship it.

Next build

Phase 11–15 · Product completion pass

The next five phases close the gap between a strong core loop and a product that feels coherent across every role, state and device. Each phase is complete only when the named user flow works end to end.

Phase 11 — One navigation and shell system

Student · teacher · leadership

Bring the school overview and Class Mode into the same navigation, skip-link, theme, focus and analytics shell as the core dashboards. Remove dead-end pages and make the current role and page obvious at every step.

Phase 12 — A complete state system

Empty · loading · error · success

Every data-driven surface must explain what is happening, what went wrong and what to do next. Add consistent retry, recovery, progress and completion states without relying on colour alone.

Phase 13 — Session and assignment resilience

Pause · resume · abandon · complete

Make bounded Practice and Timed practice sessions explicit in the student experience, preserve partial work, distinguish unfinished from completed work, and make teacher assignment progress reflect the same states.

Phase 14 — Teacher decision support

Signal → intervention → follow-up

Turn misconception volume and assignment progress into an actionable queue: identify who needs attention, choose an intervention, create or update an assignment, and see whether the next attempt improved the signal.

Phase 15 — Release-quality hardening

Accessibility · responsive · QA

Run the main flows at mobile width and with keyboard navigation, parse every inline script, check broken links and missing assets, verify reduced motion and focus visibility, and keep local product diagnostics useful without pretending they are production analytics.

Phase 5 — Bounded Forge sessions and progress continuity

Highest priority · next build

Question banks will become content pools rather than single sittings. Forge will default to a focused session of around 8 questions or 10 minutes, while smaller banks will use the questions available. Students will see session progress, save work after every answer, and be able to resume, start a new session, or change topic without losing their history.

Phase 5 — More realistic Timed practice

Same session model · timed practice

Timed practice will remain the pressure-testing mode, but five minutes should produce roughly 5–6 questions rather than 12. Longer runs can scale to 10–12 questions for 10 minutes or 20–24 for 20 minutes. Timed-out, abandoned and completed runs will be distinguishable, with partial results preserved for review in Repair mistakes.

Phase 6 — Teacher intervention loop

After session continuity

Assignment editing, clearer draft/active/completed states, stronger visibility into partial progress, and better identification of students who are repeatedly struggling.

Phase 7 — Accessibility and responsive hardening

Student and teacher surfaces

Complete keyboard navigation, form labels, focus treatment, contrast checks, mobile layouts and screen-reader announcements across the main learning and teacher flows.

Phase 8 — Design-system consolidation

Revisit earlier UI work

Consolidate repeated inline styles and shared components, standardise buttons, cards, badges, progress indicators, spacing and typography, and reduce unnecessary glow, borders and motion so Forge feels intentionally designed rather than assembled feature by feature.

Phase 9 — Deeper product intelligence

Longer-term

Adaptive question selection, stronger insight screens, better analytics, onboarding improvements and performance work once the core session model is reliable.
